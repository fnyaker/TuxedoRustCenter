## 3. Scénarios « profil piégé »

1. **Import + admin** : profil `overboost`, TDP `[1000]`, cTGP `200`. L'admin approuve « enregistrer les profils ». À l'activation : TDP `[1000]` refusé avant écriture (hors firmware), ODM inconnu refusé sans écriture (PHW-02), cTGP refusé si la borne dynamique/statique est < 200 ; si `nvidia-smi` ne fournit pas les limites, le fallback `static` 200 W s'applique et reste l'hypothèse résiduelle.
2. **Profil sans TDP** : `tdpValues: []` **n'écrit plus rien** dans le worker de profil (PHW-03) ; les maxima restent accessibles par l'action admin explicite `Admin.Hw.SetTdpValues([])`. Un profil nommé « Quiet » ne peut plus élever le TDP par ce chemin.
3. **Multi-utilisateur** : B active par `SetTempProfile` un profil enregistré par A, ou change PPD/AC pour déclencher la matrice. Le contenu reste autorisé, mais B contrôle le moment et l'état thermique.

## 4. Verdict

- **Aucun finding Critique/Élevé.**
- **PHW-02/PHW-03 : corrigés côté code** (refus ODM sans écriture, borne cTGP dynamique/statique exposée et refus hors borne, profil `tdpValues=[]` = no-op, `Admin.Hw.SetTdpValues([])` = maxima explicite). Preuve fake/CI ; matériel réel non testé.
- **PHW-04 : partiel accepté**, non bloquant : le core tolère 16 valeurs TDP pour les fichiers historiques, mais `TdpControl` refuse > 3 **avant** toute écriture. Recommandation : avertir/rejeter > 3 à l'import et afficher un résumé avant polkit.
- **PHW-05 : Info ouvert** (commentaire QML obsolète, validation locale sans contrôle d'entier) ; aucun impact sécurité.
- **PHW-06 : fermé/Info** (D4 respecté, exception io-only AH-02 documentée).
- **Mono-utilisateur : aucun bloquant** avec TR-01 documenté. Résidu non bloquant : fallback cTGP `static` 200 W si `nvidia-smi` ne fournit pas les limites (hypothèse driver non validée).
- **Multi-utilisateur : bloquant** tant que `SetTempProfile` et l'application déclenchée par l'état restent globaux et sans polkit.

**Conclusion** : le modèle « contenu autorisé à la sauvegarde, activation sans polkit » reste **acceptable en mono-utilisateur** parce que l'activation ne peut pas injecter de valeurs, que les champs sont revalidés et que les écritures repassent par les bornes matérielles (ODM refusé, TDP validé firmware, cTGP borné). Il ne l'est **pas** en multi-utilisateur sans gate d'activation.

Le seul résidu non bloquant est le fallback `static` 200 W quand `nvidia-smi` ne fournit pas les limites ; à durcir en refusant l'écriture si `source=static` pour une garantie stricte.
- Pas de test `tick` end-to-end avec offset > borne : les tests couvrent `resolve_max_ctgp_offset`/`validate_ctgp_offset` et le refus via `tick` n'est vérifié qu'en lecture de code.

- Tests QML (`tst_profile_editor`, `tst_admin_hw`) et import d'un fichier réel.
- Matériel Clevo/Uniwill, TDP PL1/PL2/PL4, rollback réel.
